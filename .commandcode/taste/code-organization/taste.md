# code organization
- Keep server-only code out of client bundles: client components/hooks must not import modules that transitively pull in `next/headers` (e.g., `api-client.ts` → `verify-token.ts`); the `"use server"` service layer is the import boundary, so client code should call those services directly and read fields off the returned result (e.g., `.data`) instead of importing shared helpers from `api-client.ts`. Fresh evidence: the same class of build error recurred (`use-invoice-download.tsx` → `api-client.ts` → `verify-token.ts` → `next/headers` in the client bundle) and the durable fix was to move the client-safe helpers (`unwrapData`/`unwrapList`/`isServiceFailure`) into `lib/utils/result.ts`, re-export them from `api-client.ts` for backward compatibility so the ~80 server-side importers keep working unchanged, and point only the client importers at the safe module. Confidence: 0.85
- Prefers modular types: one types file per module/domain instead of a single monolithic types file. Confidence: 0.9
- Prefers extracting reusable multi-entity editing UI into shared components under `components/dashboard/shared/` (e.g., `FeatureListEditor`, `KeyValueListEditor`) and reusing them across create and update forms instead of duplicating list-editing logic inline in each form. Confidence: 0.7
- Prefers implementing a cross-surface feature once as a shared client component + hook (e.g., `DownloadInvoiceButton` + `useInvoiceDownload`) and reusing it everywhere that feature appears , tables, detail pages, payment success page , rather than duplicating per-page logic. The shared flow must be used as-is (e.g., invoice = call `getOrderInvoice` → verify the result → pass to the react-pdf renderer, same as the dashboard) and never re-implemented bespoke per page; writing custom resolution/download logic in `payment-result.tsx` instead of the shared button drew a correction ("you supposed to be calling the getOrderInvoice then verify the result and pass to the react pdf renderer like dashboard ones... it should be similar and resused so logic stays same"). Confidence: 0.9
- The invoice/PDF document must faithfully reproduce the product variant the customer chose: when an order line was placed with a variant, the invoice must show the variant attributes (e.g., `Color: Black · Size: M`) and the SKU beneath the product name in small muted text (only rendered when present; non-variant lines unchanged), mirroring how the order-details pages display variants. Omitting variant details from the invoice was reported as a bug ("it is not showing variant details for variant product show them properly if the product has and user chosen variant product") and required adding `variant` to the `OrderInvoiceItem` type (same shape as `OrderProductItem.variant`) plus rendering it in the table. Confidence: 0.7
- When only a non-canonical identifier is available on a page (e.g., a gateway `tran_id` in the URL), the user expects the chain: resolve the order via the order service first (`getSingleOrder(tran_id)`) → take the order `_id` → call the entity-scoped endpoint with that `_id` (`getOrderInvoice(_id)`) → send the result to the PDF renderer. The `_id` is the canonical identifier for downstream calls, not the raw tran_id or friendly orderId ("call getSingleOrder then get the _id then use it to call the invoice data and send to the pdf renderer"). Confidence: 0.6
- Prefers centralized fixes for cross-cutting issues: fix at the source (shared service layer returning a serializable `ServiceResult` envelope + one shared `isErrorResult` helper) so all consumers benefit, rather than patching each consumer individually — when planning the error-display overhaul, the "Centralized fix" option was chosen over per-component fixes. Confidence: 0.7
