# error handling
- User-facing error messages must be abstracted from internal imp, entation details: toasts (e.g., on login/register) should show only the clean backend message (e.g., "Password does not match"), never internal error class names or wrappers like "ApiClientError: ..." / "Error: ...". Confidence: 0.85
- Failure paths of user-initiated actions must surface as friendly toaster notifications rather than silent no-ops: when a query param is wrong or the record isn't found (e.g., wrong `tran_id` / order not found on the invoice button click), show a polished `toast.error` with a clear message ("We couldn't find the invoice for this transaction...") , the user explicitly asked for "toaster error beautiful messages" in those cases. Confidence: 0.8
- Avoid `typeof x === "object"` checks for optional nested fields , `typeof null === "object"` is `true`, so it crashes with "Cannot read properties of null" when the ref is null. Prefer optional chaining (`product.brand?._id ?? ""` / `brand.createdBy && ...`) for null-safe access. Confidence: 0.7
- Prefers error results from server actions to be robustly detected on the client (serialized `{ message }` objects, not just `instanceof Error`) so error vs. success branching doesn't silently , l. Confidence: 0.6
- Expects edge cases to be handled well: defensive null/undefined guards, boundary correctness (e.g., inclusive date ranges with end-of-day on `to` for range filters), and graceful failure paths , not just happy-path implementation (repeatedly says "maintain edge cases well", "handle edge cases well", latest: "Maintain all types of edge cases.", and in the latest batch "Maintain edge cases, follow rules strictly."). Confidence: 0.85
- Custom error UI must also replace the default Next.js 404, not just catch runtime crashes: `not-found.tsx` pages at the root, public storefront, and dashboard route groups (rendering inside the segment layouts so nested and unmatched routes all get the branded friendly page with a back link and error code) , `error.tsx` alone is insufficient for 404s ("Error page not rendering on home page and dashboard pages. Make sure it renders instead of default nextjs 404, and works on nested routes."). Confidence: 0.7
- Payment result pages need a guard rail for missing expected query params (e.g., no `tran_id` on `/payment/success`): show a friendly amber "payment received but unconfirmed" card with a Return Home button (and the invoice download when an order id exists) instead of falsely claiming success ("add guard rail if tran_id display message well and keep a return button to homepage"). Confidence: 0.7
- In Next.js server actions, prefers returning serializable result objects (`{ success: false, error: "..." }`) instead of `throw new Error(...)`, because production Next.js replaces thrown server-action error messages with a generic digest warning — the client can't see the real message. Throw only in dev for locally-visible messages; in production, return the error object and let the client branch on it. Confidence: 0.85
- Error display must be consistent across ALL service modules: when any module's server call fails, the client must show the backend's actual error message in a toaster with a safe generic fallback — explicitly requested across "every service modules in client" ("they will beautifully show them to client response in toaster, not throwing bad errors but meaningful what actually happened"), implemented centrally via a serializable `ServiceResult`/`ServiceFailure` envelope from every service plus a universal `isErrorResult` check in every consumer. Confidence: 0.8
